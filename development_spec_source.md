# Техническое задание на разработку
Research and Segmentation Tool для B2B outbound

Версия 2.0 • 7 октября 2026 года

Разработать инструмент, который принимает базу контактов DealRocket, исследует компании по публичным источникам, сопоставляет наблюдения, автоматически формирует сегменты и проверяемые гипотезы, а затем выпускает отдельный генерационный промпт и исходные строки Excel для каждого сегмента.

Документ объединяет исходное ТЗ, материалы oSpaceMarketing, правила сегментации, политику исследования и последующие согласованные уточнения. При расхождениях применяется эта версия. Числовые параметры, явно обозначенные как стартовые технические настройки, допускают изменение через конфигурацию после пилота.

## Обязательный результат
- Для каждого содержательного сегмента: segment_NNN.md и segment_NNN.xlsx с общим идентификатором.
- Для нераспределённых компаний: отдельные Excel по конечным статусам, без outbound-промптов.
- Все исходные строки сохраняются без изменения значений и распределяются ровно по одному выходному Excel в рамках версии экспорта.
- Полностью автоматическая обработка без обязательного ручного утверждения сегментов.
- Минимальный стилизованный веб-интерфейс, профиль отправителя, управление запуском и повторной обработкой.

## Границы продукта
Инструмент не пишет готовые письма, не отправляет их и не управляет рассылкой. Интеграция и контракт внешнего генератора писем не входят в разработку. Выходом является самостоятельный документ с промптом по структуре предоставленного примера.

Исследуется компания, а не личная жизнь сотрудников. Контакты сохраняются из исходной базы. Публичное наблюдение не является диагнозом внутренних проблем; гипотеза всегда отделяется от факта.

## Навигация по документу
Разделы 1–4: пользовательский процесс, архитектура, данные и отправитель. Разделы 5–9: импорт, исследования, доказательства, сопоставление и сегментация. Разделы 10–13: промпты, экспорт, оркестрация и модели. Разделы 14–16: интерфейс, реализация, приёмка и план работ.

# 1 Пользовательский процесс
## Основной сценарий
1. Пользователь создаёт или выбирает профиль отправителя, проверяет офферы и загружает XLSX.
2. Система показывает листы, распознанные поля, количество контактов и предварительное количество компаний. Неподдерживаемую структуру объясняет до платной обработки.
3. Пользователь выбирает настройки исследования и общий денежный лимит, затем запускает обработку.
4. Система исследует компании, сводит результаты, обнаруживает и автоматически проверяет сегменты, классифицирует компании и создаёт выходные файлы.
5. Пользователь видит прогресс, расходы, сегменты, гипотезы и статусы; скачивает результат целиком или отдельными файлами.
6. При необходимости пользователь возобновляет остановленный запуск или повторяет обработку выбранных статусов.

## Автоматичность
Между исследованием и экспортом нет обязательного подтверждения человеком. Неопределённые случаи откладываются в статусные группы, остальные компании продолжают обработку. Просмотр результата и добровольная корректировка исходных данных не являются обязательными шагами pipeline.

## Исходный пример базы
Предоставленный файл 0002 dealrocket_employees_2026-07-25_16-21.xlsx содержит лист «Сотрудники», 9 135 строк данных и 28 колонок. Это пример для проверки совместимости, а не фиксированная схема всех будущих загрузок.

В примере есть поля контакта, компании, сайта, корпоративных и личных соцсетей, юридического названия, ИНН, выручки, численности и географии. Поля личных соцсетей сохраняются в Excel, но не используются для исследования.

## Результат для пользователя
Основной экран результата содержит название и определение сегмента, гипотезу, оффер, число компаний и контактов. По раскрытию доступны основания, источники и ограничения. В выходные Excel эти служебные данные не добавляются.

При остановке по бюджету интерфейс явно обозначает частичный результат. Необработанные строки сохраняются в статусном Excel; частичный результат нельзя показывать как завершённое исследование всей базы.

# 2 Архитектура и ответственность этапов
## Последовательность
Импорт → идентификация компаний → первичное знакомство с продуктами → обнаружение источников → исследования по направлениям → сведение профиля → признаки → сопоставление всей базы → сегменты и гипотезы → автоматическая проверка → классификация → промпты и Excel.

Порядок задаётся Python-кодом. Свободная передача управления между агентами не используется. Внутри исследовательского этапа направления и разные компании могут обрабатываться параллельно.

| Компонент | Ответственность | Выход |
| Importer и Resolver | Сохранить строки и связать их с компаниями | SourceRow, Company, Contact |
| Source Discovery | Проверить идентичность и найти источники | SourceCandidate |
| Collectors и исследователи | Получить содержание и извлечь наблюдения по направлениям | Evidence, DirectionReport |
| Сведение и Validator | Убрать повторы, проверить основания и противоречия | CompanyProfile |
| Feature Builder и сопоставление | Нормализовать признаки и найти повторяющиеся сочетания | FeatureMatrix, PatternCandidate |
| Segmentation и Hypothesis Engine | Определить гипотезы, офферы и правила | SegmentDefinition |
| Classifier | Применить зафиксированные правила | Classification |
| Prompt Architect | Создать самостоятельный промпт сегмента | SegmentPrompt |
| Exporter | Скопировать исходные строки и проверить целостность | XLSX и MD |

## Контракт передачи данных
Между этапами передаются валидируемые JSON/Pydantic-структуры. Читаемые отчёты строятся из тех же данных, а не становятся единственным источником следующего этапа. Каждое существенное наблюдение сохраняет ссылки на Evidence.

Загрузка страниц, работа с Excel, подсчёт лимитов, применение формальных правил и контроль целостности выполняются кодом. Модели используются для смыслового анализа, извлечения, обнаружения паттернов и написания промптов.

# 3 Модель данных и версии
Все сущности имеют идентификатор, версию схемы и время создания. Денежные значения хранятся с валютой; время — в UTC. Публичные даты публикаций могут быть неизвестны, что фиксируется явно.

| Сущность | Обязательное содержание |
| Run | run_id, source_file_id, sender_profile_version, config_snapshot, model_config, status, budget, timestamps |
| SourceRow | row_id, file_id, sheet_name, original_row_index, упорядоченные исходные ячейки и типы |
| Company | company_id, canonical_name, website или corporate_social, source_row_ids, identity_status, evidence |
| Contact | contact_id, company_id, source_row_id, доступные имя, роль и контакты |
| Evidence | evidence_id, company_id, URL, тип, текст/фрагмент, даты, область применимости, происхождение |
| DirectionReport | направление, статус проверки, observations, evidence_ids, contradictions, limitations |
| CompanyProfile | identity, products, audiences, current_state, marketing, market_context, signals, unknowns |
| Feature | name, value, state, confidence, evidence_ids, validity, extraction_version |
| SegmentDefinition | segment_id, version, hypothesis, offer_id, rules, angle, forbidden_claims |
| Classification | company_id, segment_version, primary_segment_id или причина отказа, matched_signals, evidence_ids |
| SegmentPrompt | segment_id, prompt_version, sender_version, текст, validation_status |
| Export | export_id, run_id, segmentation_version, состав файлов, row_mapping, checksums |

## Сохранение исходного Excel
SourceRow хранит ячейки по позиции колонки, а не только словарь по заголовку: одинаковые названия колонок не должны приводить к потере значений. Исходный XLSX сохраняется неизменяемым эталоном.

## Воспроизводимость
Для каждого результата сохраняются исходные данные, конфигурация, фактические модели и параметры, версии промптов, доказательства и правила. Это обеспечивает прослеживаемость, но не обещает побитово одинаковый ответ LLM при новом вызове.

Повторная обработка компании использует фиксированную версию сегментов. Перестроение сегментов создаёт новую версию и требует повторной классификации всей соответствующей выборки.

# 4 Профиль компании отправителя
## Форма и хранение
В интерфейсе есть отдельный раздел для создания и редактирования профиля отправителя. Первый профиль — oSpaceMarketing и Артём Кучеренко. Значения не зашиваются в бизнес-логику; каждый запуск фиксирует выбранную версию профиля.

| Блок | Поля |
| Компания | Бренд, сайт, описание деятельности |
| Юрлицо | Юридическое название, страна регистрации, ИНН или аналог, адрес; поля необязательные |
| Представитель | Имя, должность, подпись, контакты, правило формирования темы |
| Офферы | Направление, ситуации применения, ближайшие результаты, границы работ, целевые клиенты |
| Подтверждения | Кейсы, разрешённые достижения, подтверждённые факты и ограничения использования |
| Материалы | Описания услуг, примеры промптов, дополнительные документы |

## Начальное содержимое
Имя отправителя: Артём Кучеренко. Тема в создаваемом промпте: сокращённое название компании адресата + Артём Кучеренко. Начальная подпись: «С уважением, Артём Кучеренко, специалист по стратегическому развитию компаний». Подпись едина для всей серии; её изменение выполняется через профиль.

Офферы oSpaceMarketing: Marketing; Product Marketing; Business Development; Business, Market & Product R&D; Organization of Processes. Для каждого хранится описание результатов и границ из предоставленного разбора. Оффер сам по себе не является сегментом.

Рабочая формула предложения: наблюдение → возможное значение для бизнеса → ближайший результат работы → диагностический вопрос. Нельзя обещать гарантированный рост, приписывать кейсы, цены или услуги, которых нет в утверждённом профиле. Рекомендация в исходном материале не превращается автоматически в действующую услугу.

## Использование по этапам
Исследователям передаются релевантные направления и исследовательские вопросы; модели гипотез — офферы и ограничения; автору промптов — также представитель, тема и подпись. Реквизиты не добавляются в письма автоматически.

Изменение профиля не меняет старые запуски. Замена только подписи допускает повторную генерацию промптов; изменение офферов требует пересмотра зависимых гипотез и сегментов. Сохранённые актуальные доказательства можно использовать повторно.

# 5 Импорт и идентификация компаний
## Импорт
Поддержать XLSX с обнаружением фактических листов и заголовков. Не вводить предварительные фильтры компаний: выборку пользователь готовит в DealRocket. Извлечь необходимые внутренние поля, сохранив все исходные колонки, значения и порядок.

Проверять пустые строки, повторяющиеся заголовки, ссылки в ячейках и текстовые обозначения отсутствия данных. Нормализация пустых значений применяется только во внутренней модели и не меняет экспортируемые ячейки.

Для нескольких листов фиксировать, какие содержат контакты и как определён заголовок. При неоднозначной структуре показывать ошибку импорта или выбор соответствия полей до запуска исследования. Это настройка входа, не ручное утверждение сегментов.

## Правила объединения
1. Основное основание — официальный сайт, предоставленный в базе и проверенный на соответствие компании.
2. При отсутствии сайта — официальная корпоративная соцстраница, указанная в базе или подтверждённая поиском.
3. Название и юридические поля используются как подтверждение или признак конфликта. Похожее название само по себе не является основанием объединения.
4. Если основания отсутствуют или противоречат друг другу, компания получает статус NEEDS_REVIEW, без случайного объединения.

Код нормализует протокол, www, параметры отслеживания и подтверждённые перенаправления. Нельзя объединять по общему домену соцсети, каталога, конструктора или хостинга: требуется конкретная корпоративная страница/ресурс.

## Границы сущности
Исследовательская компания определяется корпоративным ресурсом. Разные юрлица одного подтверждённого бизнеса могут иметь общий профиль; независимые бренды на общем портале нельзя автоматически смешивать. Конфликт ресурса и идентичности отправляется на проверку.

Недоступный сайт не считается отсутствующим. При временной ошибке применяются ограниченные повторы и проверка корпоративных соцсетей. Состояния «не найден», «недоступен», «не подтверждён» различаются.

## Критерий завершения
Каждая исходная строка имеет row_id и внутреннюю связь с подтверждённой либо неразрешённой сущностью Company. Дубликаты строк сохраняются. Исследование одной компании не повторяется для каждого её сотрудника.

# 6 Поиск источников и исследовательские направления
## Обнаружение источников
Кратко изучить официальный ресурс для понимания продукта и аудитории, затем искать корпоративные страницы, отзывы, новости, вакансии, обсуждения продукта, альтернатив и категории. Поиск только по названию бренда недостаточен.

SourceCandidate хранит URL, тип, связь с компанией, причину релевантности и результат проверки. Обнаружение адреса и загрузка содержания — разные операции. Недоступный материал не используется как прочитанное доказательство.

## Отдельные направления
- Сайт: продукты, услуги, аудитории, позиционирование, разделение предложений, география, публичные изменения.
- Корпоративные соцсети: продуктовые сообщения, коммуникация с аудиториями, активность и позиционирование. Эти наблюдения могут стать частью гипотезы предложения.
- Вакансии и новости: рост, новые функции, регионы, продукты и направления. Приоритет — события, связанные с офферами отправителя; не ограничиваться маркетинговыми должностями.
- Отзывы и карты: повторяющиеся темы, критерии выбора, жалобы, рейтинги и даты, с различением компании и отдельных филиалов/продуктов.
- Форумы и продуктовый контекст: задачи пользователей, альтернативы, барьеры и обсуждения категории. Категорийные выводы не приписываются отдельной компании.

## Сбор и отчёты
Основной crawler — Crawl4AI; Browser Use применяется для сложных динамических страниц. Нельзя обходить авторизацию, CAPTCHA, paywall и закрытые аккаунты. Повторяющиеся тексты и меню удаляются до передачи модели, но доказательные фрагменты сохраняются.

Каждый DirectionReport содержит observations, источники и фрагменты, даты, противоречия, неизвестное, выполненные поиски и причины завершения. Предварительные интерпретации выделяются отдельно. Задача — собрать достаточную релевантную информацию, а не всю историю компании.

## Готовность направления
Использовать статусы COMPLETE, NO_RESULTS, UNAVAILABLE, LIMIT_REACHED, FAILED. Отдельный исследователь завершает только своё направление. Следующий этап получает отчёты всех направлений либо явные причины отсутствия результата; два удобных подтверждения на сайте не отменяют проверку соцсетей и отзывов.

# 7 Доказательства и актуальность
## Evidence
Для существенного наблюдения обязательны evidence_id, URL, source_type, retrieved_at, published_at при наличии, текстовый фрагмент, scope company/product/category и связь с company_id. Хранить первоисточник или группу происхождения для распознавания перепечаток.

Наблюдение должно быть подтверждено фрагментом. Неизвестное остаётся unknown. «Не найдено на проверенных страницах» не означает «в компании отсутствует». Наличие сайта, CRM-виджета или вакансии не доказывает качество внутренних процессов.

## Независимость и уверенность
Гипотеза для классификации требует минимум двух содержательно разных подтверждающих сигналов с независимым происхождением. Разные страницы одного сайта и копии одного сообщения не дают два независимых подтверждения. Корпоративная публикация и её перепечатка в соцсети относятся к одному происхождению. Разные типы источников предпочтительны, но не заменяют проверку независимости.

HIGH: прямое актуальное подтверждение, надёжная идентификация и отсутствие существенных противоречий. MEDIUM: косвенное обоснование с явно указанной неопределённостью. LOW: слабое, устаревшее или существенно противоречивое основание.

Обязательные признаки сегмента требуют HIGH, поддерживающие — HIGH или MEDIUM. LOW не влияет на итоговую классификацию. Гипотезы HIGH и MEDIUM допустимы при выполнении порога независимости; MEDIUM требует осторожной формулировки. Даже HIGH не превращает гипотезу во внутренний диагноз.

| Сигнал | Стартовое окно актуальности |
| Посты и сообщения в соцсетях и на форумах | Последние 30 дней от запуска |
| Описание профиля, закреплённый материал, продукт | Базовый контекст с проверкой применимости |
| Активный найм и новая вакансия руководителя | 90 дней |
| Изменения команды и прочая маркетинговая активность | 6 месяцев |
| Продукт, направление или новый рынок как событие | 12 месяцев |
| Отзывы о текущей ситуации | 12 месяцев |
| Текущие услуги, филиалы и география | Текущее подтверждённое состояние |

В старой форумной теме читаются свежие сообщения и необходимый контекст. Отсутствие свежих постов не доказывает заброшенность канала. Для датированных триггеров общий ориентир — 6 месяцев, с указанными исключениями для найма и запусков. Неизвестная дата не заменяется датой загрузки. Новое окно 30 дней заменяет прежние окна 6 месяцев для социальной активности и 24 месяца для форумных сообщений.

# 8 Глубина исследования и отдел сопоставления
## Ресурсные лимиты
| Параметр на компанию | Стартовое значение |
| Базовые поисковые запросы | До 6 суммарно по направлениям |
| Релевантные страницы сайта | До 8 |
| Внешние материалы новостей, вакансий и публикаций | До 8 |
| Корпоративные социальные платформы | До 3 |
| Источники отзывов и форумных обсуждений | До 5 суммарно |
| Уточняющие повторные поиски одного вопроса | До 2, внутри общего лимита |
| Общий резерв целевого доисследования | До 3 запросов и 5 страниц/материалов |

Сайт, соцсети, отзывы и внешний контекст имеют отдельные счётчики; соцсети и отзывы не расходуют лимит восьми новостных/внешних материалов. Общий лимит поисковых запросов координируется кодом между направлениями. Указанные максимумы не являются обязательными квотами.

Чтобы одна платформа или длинная тема не обходила лимиты, конфигурация дополнительно ограничивает сообщения, страницы, символы и токены на направление. Начальные инженерные пределы: до 30 материалов одной соцплатформы и до 30 релевантных сообщений на источник отзывов/форум; выборка и ограничения явно фиксируются.

Доисследование отвечает на конкретный вопрос и использует один резерв на компанию в запуске. Допускается не более одного возврата к этому этапу после сопоставления. Технические повторы не создают новые исследовательские бюджеты.

## Остановка
Завершить минимальную проверку каждого направления и поиск опровержений. После этого прекратить углубление, если данных достаточно, либо остановиться по лимиту с явным указанием недостаточности. Исчерпание лимита само по себе не является технической ошибкой.

## Сведение и сопоставление
Сначала объединить отчёты одной компании, удалить повторы, разрешить или обозначить противоречия и создать CompanyProfile. Затем нормализовать признаки: масштаб и сложность, изменения, маркетинговые наблюдения, продуктовые аудитории, клиентские темы, спрос и публичные процессные сигналы.

Каждый признак хранит значение, состояние confirmed/refuted/unknown, confidence и evidence_ids. LOW не используется для решения. По всей базе строится матрица и находятся повторяющиеся сочетания, характерные примеры и исключения. Модели получают компактные сводки с доступом к исходным основаниям, а не полный массив всех документов одним запросом.

# 9 Сегменты гипотезы и классификация
## Discovery
Сегмент — группа компаний с общей проверяемой гипотезой, релевантным оффером и единой стратегией обращения. Отрасль, размер, регион или отдельный запуск не образуют сегмент сами по себе. Segment задаёт гипотезу; Trigger объясняет актуальность обращения; Context помогает интерпретации.

Модель получает паттерны всей базы, характерные профили и исключения. Формирует candidate segments и связывает их с офферами. Статистическая группа становится сегментом только после смысловой проверки.

## SegmentDefinition
Обязательны segment_id, version, name, description, offer_id, observed_pattern, hypothesis, why_it_may_matter, required_signals, supporting_signals, contradicting_signals, relevant_triggers, outreach_angle, diagnostic_question, allowed_claims и forbidden_claims.

Правила сохраняются в ограниченном машинно-исполняемом формате: all/any/not над признаками с операторами eq, in, gte, lte, exists и проверками confidence/freshness. Исполняемый код, сгенерированный моделью, не допускается. NOT unknown не означает подтверждённое отсутствие.

## Автоматическая проверка
Проверить ясность одной основной гипотезы, публичные основания, соответствие офферу, выполнимость правил, отличимость коммуникации и полезность отдельного промпта. Сходные по гипотезе и стратегии сегменты объединить, после чего заново проверить правила. Проверка выполняется отдельным вызовом модели; формальная валидность — кодом.

Технический стартовый предел — две итерации исправления определения. Не прошедший проверку кандидат не публикуется. Минимальный коммерческий размер не фиксируется; небольшой сегмент сохраняется при содержательной самостоятельности, но единичный случай не объявляется повторяющимся паттерном.

## Classification
Зафиксированные правила применяются ко всем компаниям кодом. Все required должны выполняться с HIGH; сильное подтверждённое опровержение исключает кандидат. Дополнительные подтверждения не компенсируют исключающее противоречие.

При нескольких подходящих сегментах последовательно сравнить качество оснований, прямоту связи, отсутствие противоречий, соответствие офферу, специфичность обращения и актуальный trigger. Для каждой ступени использовать описательные категории с примерами, без искусственных весов. Нет обоснованного победителя — AMBIGUOUS; нет подходящего сегмента при достаточных данных — UNCLASSIFIED.

Сохранять matched_signals, contradicting_signals, triggers, evidence_ids и classification_reason. Гипотеза сегмента может использоваться для конкретной компании только при её собственных достаточных основаниях, а не по доказательствам других участников группы.

# 10 Генерационные промпты
## Назначение
Создавать один самостоятельный UTF-8 Markdown-файл на каждый итоговый сегмент. Промпт предназначен для внешней генерации темы и четырёх писем. Никаких интеграционных обязательств по внешнему генератору в проекте нет.

Пример «Предварительный Промпт.docx» задаёт структуру и общие правила. Его управленческая гипотеза, описание встречи и программа развития не копируются во все сегменты: они заменяются новым оффером, гипотезой и релевантным результатом.

## Обязательные части
1. Роль, задача, цель обращения и данные отправителя.
2. Определение сегмента, наблюдаемый паттерн и одна основная гипотеза.
3. Оффер и ближайший результат, который допустимо обсуждать.
4. Правила выбора фактов из доступных INPUT_ROW_DATA и поведения при их недостатке.
5. Разрешённые и запрещённые утверждения; осторожный язык гипотез.
6. Логика четырёх писем, тон, тема, обращение и подпись.
7. Строгий формат результата: «Тема письма», «Письмо 1», «Письмо 2», «Письмо 3», «Письмо 4», без пояснений после серии.

## Последовательность и тон
Первое письмо — наблюдение и проверка интереса. Второе — узнаваемая ситуация и новый угол. Третье — последний контакт и конкретизация результата. Четвёртое — после положительного ответа, переход к ознакомительной встрече; это не очередной холодный follow-up.

Писать от первого лица, коротко, по делу, без комплиментов ради комплиментов, URL и Markdown в итоговых письмах. Не обещать гарантированный рост, не критиковать руководство, не создавать впечатление диагностики без данных. Четвёртое письмо может быть подробнее.

Имя в строке «Письмо адресовано» ставится в дательный падеж; при отсутствии имени используется корректное обращение к ответственному руководителю. В четвёртом письме этой строки нет. Данные темы и подписи берутся из версии профиля отправителя.

## Достоверность и проверка
Исследование определяет стратегию сегмента. Конкретный факт об адресате в письме допустим только если доступен в INPUT_ROW_DATA. Промпт не требует скрытого CompanyProfile и не предполагает обязательного наличия полного текста сайта.

Если фактов мало, письма раскрывают разные аспекты гипотезы без выдумывания новых фактов. Проверить структуру, соответствие офферу, ограничения, отсутствие неподтверждённых обещаний и отличие от других сегментов. Ошибка промпта исправляется ограниченно; невалидный файл не выдаётся как готовый.

# 11 Экспорт и конечные группы
## Структура результата
output/prompts/segment_001.md
output/databases/segment_001.xlsx
output/statuses/INSUFFICIENT_DATA.xlsx
output/statuses/AMBIGUOUS.xlsx
output/statuses/UNCLASSIFIED.xlsx
output/statuses/NEEDS_REVIEW.xlsx
output/statuses/FAILED.xlsx
output/statuses/NOT_PROCESSED.xlsx

Статусные файлы создаются только при наличии строк. Для них промпты не создаются. NOT_PROCESSED применяется к частичному экспорту после остановки. Готовые сегменты выдаются только при наличии валидной пары MD и XLSX. Технические manifests и отчёты остаются внутренними; архив скачивания может содержать пользовательские файлы.

## Неприкосновенность данных
Сохранять названия листов с исходными данными, заголовки, порядок колонок, значения, типы ячеек и относительный порядок строк внутри листа. Дубликаты не удалять. Служебные колонки не добавлять. Форматирование сохранять по возможности.

Исходный файл не изменять. Для формул, объединённых ячеек и межлистовых зависимостей выполнять preflight: если перенос строк нарушит значения или структуру, явно отклонить неподдерживаемый файл до исследования, а не молча упрощать его. Минимальная поддерживаемая база — табличный XLSX с независимыми строками, как предоставленный пример.

## Приоритет конечной группы
Техническая ошибка без пригодного результата после повторов → FAILED. Неподтверждённая идентичность или неразрешимый конфликт фактов → NEEDS_REVIEW. Незавершённая обработка из-за паузы → NOT_PROCESSED. Недостаточность доказательств → INSUFFICIENT_DATA. Несколько равных сегментов → AMBIGUOUS. Достаточное исследование без подходящего сегмента → UNCLASSIFIED. Иначе — один primary segment.

Причины и внутренние статусы хранятся отдельно от этой единственной группы. Ошибка необязательного источника не должна автоматически превращать пригодный профиль в FAILED.

## Контроль целостности
Сумма строк всех сегментных и статусных Excel равна числу исходных строк данных. Проверять биекцию row_id → экспортированная строка, равенство значений и типов, заголовков и порядка; одного сравнения количества недостаточно.

Экспорт атомарный: сначала временная сборка и проверка, затем публикация версии. Повторная обработка создаёт новую согласованную версию файлов без дублирования строк; предыдущий экспорт остаётся доступен как отдельная версия.

# 12 Оркестрация ошибки и бюджет
## Независимые состояния
| Уровень | Примеры состояний |
| Выполнение запуска | CREATED, RUNNING, PAUSING, PAUSED, COMPLETED, COMPLETED_WITH_ISSUES, FAILED |
| Этап компании | PENDING, RUNNING, SUCCEEDED, RETRY_REQUIRED, FAILED |
| Исследование | COMPLETE, INSUFFICIENT_DATA, NEEDS_REVIEW |
| Классификация | PENDING, ASSIGNED, AMBIGUOUS, UNCLASSIFIED |
| Направление | COMPLETE, NO_RESULTS, UNAVAILABLE, LIMIT_REACHED, FAILED |

Не смешивать результат исследования, техническую ошибку и результат классификации в одном поле. Исходные названия MANUAL_REVIEW и NEEDS_REVIEW нормализуются в NEEDS_REVIEW; этот статус не требует остановки всей базы.

## Возобновление и повторы
Этап записывает результат и checkpoint атомарно. Повтор использует ключ run_id/company_id/stage/input_version и не создаёт дубликаты. Выполняется только незавершённый или признанный невалидным этап и его зависимые этапы.

Для сетевых ошибок и ограничений частоты использовать backoff и ограниченные повторы. Стартовая настройка — до двух повторов этапа сверх первой попытки. Отсутствие публичной информации не лечится бесконечными повторными вызовами модели.

Версии сегментов фиксируются до классификации. Повтор статусов по прежним правилам не меняет определения; отдельное перестроение создаёт новую segmentation_version. Доисследование, изменение офферов или профиля инвалидирует только зависимые результаты.

## Учёт расходов
Сохранять input/output tokens, доступные данные reasoning/cache, модель и параметры, поисковые запросы, загруженные страницы, внешние материалы, browser runs, retries, время и estimated_cost. Стоимость рассчитывается по версионируемому тарифу, без двойного подсчёта включённых токенов.

Общий денежный лимит задаётся до запуска. Перед платной операцией резервировать оценку максимальной стоимости с учётом пределов ответа; после завершения сверять фактическое использование. Если цены или верхняя оценка неизвестны, не запускать неконтролируемую платную операцию. Дополнительно применять лимит API-проекта, где он доступен.

При исчерпании бюджета прекращать новые платные операции, сохранять промежуточные результаты и показывать причину паузы. Уже зарезервированные операции могут корректно завершиться. После увеличения лимита продолжить с checkpoint. Лимит стоимости на компанию не обязателен в первой версии; ресурсные лимиты обязательны.

## Настройки по роли
Конфигурация содержит model_id, reasoning_effort, max_input_tokens, max_output_tokens, timeout, retry_limit и fallback_model. Стартово использовать low для поиска и извлечения, medium для сведения и генерации, high для гипотез и смысловой проверки; допустимость значений проверять по API выбранной модели.

Не повышать модель только потому, что нет источников. Причины повышения: невалидная структура после исправления, сложная идентификация или неразрешённое смысловое противоречие. Передавать резервной модели только спорный фрагмент и необходимые основания.

## Экономия и оценка
Исследовать компанию один раз, удалять дубли, передавать компактные отчёты, повторно использовать актуальные evidence и выносить механические операции в код. Сильная модель работает преимущественно по сводкам и сегментам, а не по всем сырым страницам.

На пилоте сравнить Luna и Sol по пропускам, неверным фактам, противоречиям, полезности гипотез и полной стоимости с повторами. Снижение тарифа не считается экономией, если растёт доля ошибок и повторных запусков.

# 14 Интерфейс и серверные операции
## Визуальное направление
Компактный профессиональный веб-интерфейс: ясная типографика, спокойная палитра, один акцентный цвет, понятные состояния. Приоритет — загрузка, запуск, прогресс и получение результата. Детали модели и технические поля размещаются в расширенных настройках.

## Основные экраны
- Профили отправителя: компания, юрлицо, представитель, офферы, материалы и версии.
- Новый запуск: загрузка XLSX, проверка структуры, выбор профиля, бюджет и настройки.
- Выполнение: контакты и компании, прогресс направлений и этапов, расходы, проблемы, пауза и продолжение.
- Результаты: сегменты, гипотезы, офферы, размеры групп, скачивание пары или всего результата.
- Статусные группы: причины, количество компаний и контактов, повторная обработка.
- Детали компании: профиль, evidence, противоречия и объяснение классификации по раскрытию.

Нет кнопки обязательного утверждения сегментов. Редактирование исходных сведений пользователем возможно через профиль/новый вход или повторный запуск; исходный Excel внутри существующего запуска неизменяем.

## Минимальные серверные операции
Создание и версионирование sender profile; загрузка и preflight файла; создание/старт run; чтение прогресса; pause/resume; повтор выбранных компаний/статусов; получение сегментов, профилей и evidence; создание и скачивание экспорта.

Долгие операции выполняются фоновой задачей, а не внутри HTTP-запроса. API возвращает идентификатор операции. Прогресс можно получать polling или SSE. Ошибки содержат понятное сообщение, этап, возможность повтора и технический идентификатор для журнала.

## Работа с материалами
В первой версии профиль принимает текст и документы MD, TXT, DOCX. Загруженные материалы сохраняются с версией. Данные компании-отправителя не смешиваются с исследуемыми компаниями. Извлечённые предложения о новых услугах не становятся подтверждёнными офферами без сохранения пользователем в профиле.

## Доступ
Стартовый вариант — приложение для одного пользователя в локальном Docker-окружении, без многопользовательской панели. Это техническая база первой версии. Публикация в интернете требует отдельной настройки доступа; приложение по умолчанию не открывает базу контактов в публичную сеть.

# 15 Реализация и проверки
## Рекомендуемый стек
Python 3.12; FastAPI для серверного API; Pydantic для контрактов; PostgreSQL, SQLAlchemy и Alembic для хранения; asyncio/httpx для конкурентной работы; OpenAI SDK/Agents SDK для моделей и tracing при управлении этапами кодом; Crawl4AI и Browser Use; openpyxl для точного XLSX; React и TypeScript для интерфейса; Docker Compose; pytest.

Стек конкретизирует исходную рекомендацию. Версии зависимостей фиксируются после совместимой пробной сборки. Отдельный worker выполняет долгие задачи; состояние очереди и checkpoints хранится устойчиво, а не только в памяти процесса.

## Структура проекта
backend/app: importer, resolver, discovery, collectors, extractors, profiles, validation, features, comparison, segmentation, hypotheses, prompts, exporter, orchestration, storage, api.

Отдельно: schemas, prompt_templates, config, migrations, tests/unit, tests/integration, tests/fixtures, frontend, deployment. Пользовательские файлы и секреты не включаются в репозиторий.

## Обязательные проверки
- Импорт и экспорт: дубликаты, одинаковые заголовки, пустые значения, несколько листов, отсутствие сайта, сохранение типов и порядка.
- Resolver: разные записи одного ресурса, соцстраницы общего домена, конфликт названия и сайта, самостоятельные компании на общем портале.
- Evidence: перепечатки, неизвестная дата, устаревший сигнал, категорийный контекст, опровержение, неизвестное вместо ложного отрицания.
- Сегментация: выполнение required, исключающие признаки, равные кандидаты, отказ от LOW, объяснимость и версия правил.
- Оркестрация: авария между этапами, повтор без дубликатов, ограничение retries, пауза по бюджету и возобновление.
- Промпты: структура серии, отправитель, оффер, отсутствие скрытой зависимости от research и неподтверждённых обещаний.

## Работа с внешними данными
API-ключи хранить в environment/secrets, не в промптах и журналах. Внешние страницы рассматриваются как данные: инструкции внутри них не управляют агентом. Ограничить размеры загрузок, допустимые протоколы и обращения к локальным/служебным сетевым адресам через пользовательские URL.

Не обходить закрытый доступ. Личные соцсети сотрудников не исследовать. Логи не должны дублировать контактную базу без необходимости. Сохранять доступные источники и даты для аудита; результат модели не становится доказательством сам по себе.

# 16 План работ и приёмка
## Порядок реализации

4. Сведение профилей, проверка evidence, признаки и сопоставление базы.
5. Автоматическое формирование и проверка сегментов, классификация и статусные группы.
6. Генерация и проверка промптов, согласованный экспорт файлов.
7. Сквозной пилот на небольшой разнообразной выборке; сравнение моделей и стоимости.
8. Стилизованный интерфейс, управление бюджетом, пауза и повторная обработка.
9. Проверка полной базы, настройка параллельности, Docker-сборка и инструкция запуска.

## Критерии приёмки
Исходный файл не изменён. Каждая исходная строка присутствует ровно в одном выходном Excel; значения, заголовки и порядок сохранены. Все контакты одной компании находятся вместе.

У значимых наблюдений есть доказательные фрагменты и URL. Неизвестное не превращается в отрицание, перепечатки не увеличивают независимость подтверждений. Каждое исследовательское направление имеет результат или явную причину его отсутствия.

Сегменты автоматически проверены, имеют исполняемые правила и различающиеся гипотезы. Назначение каждой компании объясняется собственными признаками. Нераспределённые компании находятся в статусных Excel без промптов.

Для каждого опубликованного содержательного сегмента есть валидная пара MD/XLSX. Промпт содержит данные выбранной версии отправителя, релевантный оффер и структуру четырёх писем; не требует скрытых исследовательских полей.

Остановка и перезапуск не повторяют уже завершённую работу без причины. Расходы и лимиты видны, бюджет учитывает выполняющиеся операции. Выбор модели и причины повышения отражаются в журнале. Интерфейс позволяет пройти путь от загрузки до скачивания без обязательного ручного согласования этапов.
