# Сводное решение специалистов

Дата: 9 октября 2026. Основание: read-only аудит кода, предыдущие замеры и сообщение пользователя о балансе $48,56. Исходное задание: specialist-research-brief.md. Реализация рабочего конвейера в этой фазе не менялась, платные запросы не выполнялись.

## Решение

Не начинать с замены всех моделей бесплатными и не продолжать массовый прогон. Порядок: доказательность и учёт → прямой сбор → поисковый план по пробелам → безопасная конкурентность → сравнение моделей на одинаковых входах.

### Экономика

$1,44 — изменение баланса, сообщённое пользователем; $1,9058 — внутренняя оценка с запасными множителями; $1,65 — сценарий без множителей. Это три разные величины. Для сверки нужны одинаковое временное окно, cached tokens, число tool calls, дата тарифа и другие операции аккаунта. Запрещено подгонять тариф по коэффициенту отношения балансов.

При предположении текущего кода $0,01 за поисковую операцию:

| Среднее операций поиска на компанию | Поиск по 7 675 компаниям, без токенов |
|---|---:|
| 1 | $76,75 |
| 0,5 | $38,38 |
| 0,25 | $19,19 |
| 0,1 | $7,68 |

Следовательно, объединение поиска в один вызов на компанию не обеспечивает ориентир $50. Нужна существенная доля компаний с доказанным покрытием через прямой сбор и общие источники; если это недостижимо без потери качества, честно пересмотреть ориентир, а не скрывать пропущенные направления.

### Новый сбор

1. Прочитать исходный ресурс; не отвергать принадлежность компании только по неудаче поисковой выдачи.
2. Извлекать href, rel, социальные ссылки, контакты и реквизиты до удаления nav/footer. Сейчас сборщик удаляет эти элементы и не возвращает ссылки.
3. Обходить небольшой целевой набор страниц, сохраняя исходный/конечный URL и основания принадлежности.
4. Вести матрицу покрытия направлений, отдельно отмечая «проверено», «нет данных», «ограничен доступ», «устарело», «противоречие».
5. Формировать общий поиск оставшихся пробелов и адресные дополнительные вопросы. Не считать направление проверенным только потому, что на сайте не нашлась ссылка.
6. Кэшировать robots/DNS/страницы с TTL; не вечный отрицательный кэш. Категорийные материалы переиспользовать с сохранением scope=category.

### Надёжная очередь

Один координатор выдаёт ограниченный пул задач разных компаний, стартовая конкурентность 3, измерение также при 1/2/4. Каждой задаче — отдельный Gateway и Session. Направления одной компании пока последовательны: общий research JSON обновляется read-modify-write и не выдерживает независимых конкурентных записей.

Нужны атомарный claim, owner/lease, revision, стабильные company/stage/input идентификаторы. Run.stage отражает крупную фазу, а стадии компаний хранятся отдельно. Сегментация запускается после барьера завершения company jobs.

Дата research_as_of фиксируется для версии исследования. Сейчас payload использует текущую дату: продолжение на следующий день меняет cache key и может повторить оплаченный запрос. Сохранять checkpoint каждого extraction chunk, а не только всего направления.

Pause прекращает выдачу новых задач; уже отправленные запросы завершаются и сохраняются. Неизвестный исход остаётся UNCERTAIN и не повторяется автоматически. Абсолютное exactly-once внешнего API после сетевого разрыва не обещается.

Общий limiter учитывает RPM/TPM, Retry-After и jitter, плюс доменный limiter для HTTP. SQLite уже использует WAL и timeout, расходы обновляются атомарно; менять БД только ради четырёх задач преждевременно. Сначала измерить lock waits на коротких транзакциях.

### Качество прежде смены модели

Два дефекта воспроизведены специалистом на синтетических входах без сети:
- social evidence с датой, отсутствующей в исходном тексте, сохраняется как HIGH;
- два фрагмента одного первоисточника на сайте компании и её VK могут пройти правило независимости по разным доменам.

Следовательно, local/cloud требуют одинаковой независимой валидации. published_at должна иметь основание в источнике (фрагмент/метаданные), иначе null. retrieved_at хранится отдельно. Источник, издатель/автор и исходный факт должны быть различимы; разные типы источников важны, но сами по себе не доказывают независимость.

Семантическую роль evidence и реальное опровержение проверять отдельно: отсутствие информации — limitation, не contradiction. LOW и category не должны проникать в назначение через обходные supporting-признаки.

### Порядок внедрения и проверки

1. Добавить регрессионные тесты на неподтверждённую дату, зеркала/перепечатки, corporate cross-post, unknown vs refuted, продолжение на следующий день.
2. Исправить валидацию и учёт; существующие результаты не переписывать без версии и аудита.
3. Реализовать source-first на отдельной ветке и сохранённых/контрольных HTTP-ответах.
4. Реализовать очередь и fault injection без платных API; убедиться в отсутствии дубликатов и потерь.
5. Сравнить локальную и облачную обработку на одинаковых сохранённых материалах и ручной разметке. Бесплатный облачный сервис — только отдельный вариант после проверки квот и условий данных.
6. Подготовить конкретную смету небольшого live-теста и отдать на согласование. После измерения выбрать режим и только затем продолжать большую базу.

Критерий выбора: меньше стоимость полезного профиля при сохранении evidence-качества и покрытия, плюс измеренное уменьшение времени. Подмена этого критерия числом PROFILE_READY запрещена. Доказательный вывод «гипотезы нет» может быть полезным результатом; недоисследованность нельзя выдавать за экономический успех.

## Дополнение: допуск моделей и ответственность

Работу разделили между тремя исследовательскими агентами: сбор источников и стоимость; конкурентность и надёжность; качество моделей и происхождение доказательств. Ведущий агент сопоставил выводы и составил этот документ. Это проект решения, а не уже внедрённая оптимизация.

Инженеру качества следует разметить имеющиеся 102 страницы и результаты 22 подтверждённых/5 отклонённых компаний; частично обработанную компанию учитывать отдельно. Облачные ответы не являются эталоном. Разметка включает фрагмент и его позицию, субъект, scope, дату с основанием, издателя, первоисточник, семейство перепечаток и связь с гипотезой. Часть примеров оставить для контрольного сравнения; спорные случаи проверять независимо.

Модель должна выбирать ID сохранённого фрагмента, а цитату восстанавливает приложение. Для даты различать публикацию, обновление, событие и получение. Правила актуальности проверять кодом по типу события и фиксированной дате исследования: сейчас news/jobs/reviews могут получить current=True без такой проверки. После удаления недействительных доказательств пересчитывать сигналы и пригодность профиля.

Предлагаемые, ещё не достигнутые критерии: ноль ошибочных компаний, выдуманных цитат/дат, подмен company/category и ложных независимых подтверждений на контрольной выборке; точность подтверждённых утверждений не ниже 95%; полнота относительно исправленного облачного варианта не ниже более чем на 5 процентных пунктов. Для каждого направления нужен результат или явная причина отсутствия. Маленькая выборка не гарантирует качество на всей базе.

Предыдущий локальный тест Qwen3 4B: три документа, 8/9 точных цитат, 9/9 неподтверждённых дат, 19–32 секунды на документ. Он не доказывает преимущество или отставание от облака: входы не были одинаковыми. Локальной модели можно предложить выбор фрагментов, тип страницы, явные продукты/аудитории и нормализацию признаков. Спорную идентичность, независимость источников и финальные персональные утверждения пока ей автономно не поручать.

Извлечение составляет около 6,6% текущей внутренней оценки расходов, вместе со сводкой — около 9,8%. Поэтому бесплатная замена этих стадий не решает основную экономическую проблему. Локальные модели не требуют оплаты API, но используют оборудование и время; ускорение должно быть измерено отдельно.

Для очереди обязательны испытания pause/restart, повторной доставки job, 429/Retry-After, timeout с неизвестным результатом, неверного JSON и смены календарной даты. Сравнивать одинаковые фикстуры при конкурентности 1/2/3/4: время, память, блокировки БД, число операций, суммы и полноту сохранённых отчётов. Синтетическое ускорение не выдавать за измеренную скорость реальных API.
